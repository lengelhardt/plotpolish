# plotpolish — design notes (0.1)

This document records the plan and the reasoning behind the decisions that
are *not* obvious from the code. The non-negotiable design rules are in the
README; this file explains how they are implemented.

## One-paragraph summary

`plotpolish` is a framework-free Web Component (`<plotpolish-panel>`) that
lets a user pick matplotlib style defaults with ordinary form controls and
writes the result into their Python source as **one fenced, regenerated
block** of plain matplotlib code. It talks to the host through two tiny
interfaces — `FigureBackend` (run Python, get JSON back) and `CodeSink`
(read/write the user's source). A small Python helper module, shipped
*inside* the JS bundle as a string, does the matplotlib-facing work:
listing styles, introspecting the live figure, and applying live-preview
equivalents to it.

## Where things live, and why

| Concern | Lives in | Why |
| --- | --- | --- |
| Control metadata (keys, types, defaults, live/re-run category, labels) | `src/schema/controls.json` | Single source of truth. TS imports it directly. pytest reads it **only in tests** for contract checks; the Python runtime never needs it. |
| Fenced block generate / parse / upsert / remove | **TypeScript** (`src/block.ts`, `src/pylit.ts`) | See "Generator in TS, not Python" below. |
| `list_styles`, `set_style`, `introspect_figure`, `apply_live` | **Python** (`python/plotpolish/core.py`) | These need matplotlib. Pure functions, JSON in/out, no state, imports limited to `matplotlib`, `json`, `math`. |
| Executability of generated blocks | pytest, via golden fixtures | Vitest asserts the generator reproduces `python/tests/fixtures/blocks/*.py`; pytest `exec`s the same files on matplotlib 3.8 and 3.10 and checks the resulting `rcParams`. This is the cross-language contract. |

### Generator in TS, not Python

The brief allowed either. TS wins for three reasons:

1. **The source of truth for the user's code is the JS side.** `CodeSink`
   is synchronous; the editor buffer is a JS string. Replacing a fence is a
   text operation on that string, and doing it through an async Python
   round-trip would make every control change wait on the interpreter.
2. **The panel must work with no interpreter at all.** The clipboard sink
   has no Python behind it, and in Pyodide hosts the panel is useful
   *before* the (tens of MB) runtime has finished loading.
3. **Parsing the block back is the only persistence.** That parse has to
   happen when a file is opened, again before Python is necessarily up.

The cost is a tiny Python-literal reader in TS (`pylit.ts`). It handles
exactly the grammar the generator emits — string keys; `int`/`float`,
`True`/`False`, `"str"`, flat lists of numbers or strings, and
`mpl.cycler(color=[...])` — and rejects everything else. That is a
feature: a block the tool did not write is surfaced as an error, not
silently reinterpreted.

Python still has a say: pytest executes the golden blocks and checks that
every emitted key is a real rcParam on both supported matplotlib versions,
and that the values validate.

## The block

```python
# --- plot style (generated by plotpolish; edit above, not here) ---
import matplotlib as mpl
mpl.style.use("seaborn-v0_8-whitegrid")
mpl.rcParams.update({
    "font.size": 12,
    "axes.grid": True,
})
# --- end plot style ---
```

The golden copies of this format live in `python/tests/fixtures/blocks/`.

* **`mpl.style.use(...)` is emitted only for a named style.** The block
  never calls `style.use("default")`. In a long-lived interpreter that would
  reset every non-blacklisted rcParam *mid-program*, including values the
  host sets before each run: Trinket sets `figure.autolayout = True` on both
  of its Pyodide paths and a pane-fitting `figure.figsize` on the worker
  path, and the block runs after that setup. Leftover rcParams from a
  previously applied style are a real problem in a persistent interpreter,
  but they are a *session* problem, so they are fixed in the session: when
  the user changes the style dropdown, the panel calls `set_style(name)`,
  which resets to library defaults and applies the new style between runs.
  The host's per-run setup then restores its own values on the next run.
  Hosts pass the keys they own as `panel.hostRcKeys`, and `set_style`
  preserves them.
* **A named style carries the host's keys across `mpl.style.use`.** The
  per-run setup above runs *before* the block, so it does not protect a key
  the style sheet itself sets: 8 of matplotlib's 29 styles set
  `figure.figsize`, `seaborn-v0_8` among them, and it is one of the eight
  curated style buttons. When there is a named style and `hostRcKeys` is
  non-empty, the block saves those keys, applies the style, puts them back
  and deletes the name it used:

  ```python
  import matplotlib as mpl
  # Hold on to the values this page set, so the style below does not replace them.
  _plotpolish_host_rc = {k: mpl.rcParams[k] for k in ["figure.autolayout", "figure.figsize"] if k in mpl.rcParams}
  mpl.style.use("seaborn-v0_8")
  mpl.rcParams.update(_plotpolish_host_rc)
  del _plotpolish_host_rc
  ```

  The restore lands before the block's own `rcParams.update`, so a key the
  student set still beats both the style and the host. With no named style
  nothing would reset the keys and the block is byte-identical to one with
  no host keys. `parseBlock` recognizes these lines and skips them: the
  host, not the block, is the authority on which keys it owns.
* **A fully default state produces no block.** Style `"default"` with no
  keys set means there is nothing to say; `upsertBlock` removes an existing
  fence rather than writing an empty one.
* **Only touched keys are emitted.** Panel state is
  `{ style, rc: { key: value } }`; a control the user never changed does not
  appear. Reset clears `rc` and sets `style` to `"default"`.
* **Placement:** top of file, after shebang / encoding line / module
  docstring / `from __future__` imports. rcParams are read when artists are
  created, so the block must run before the user's plotting code.
* **Idempotent:** one existing fence is replaced in place. Two or more start
  or end markers, or a start without an end, is a `FenceError` the panel
  shows and refuses to write over.
* `axes.prop_cycle` is emitted as `mpl.cycler(color=[...])` rather than the
  string form matplotlib also accepts, because students read this block.
* `savefig.bbox` uses `"standard"` (matplotlib's accepted spelling of
  `None`) so the dict stays a literal.

## Live preview categories

Every control declares one of three categories in `controls.json`:

| Category | Meaning | UI |
| --- | --- | --- |
| `live` | Has an artist-level equivalent; `apply_live` changes the retained figure immediately. | Applies on change. |
| `save` | Read by `savefig`, not by artists; `apply_live` sets the rcParam so the next save honors it. | Labeled "applies when saving". |
| `rerun` | rcParams-only. Today only the style sheet (handled by `set_style`); color cycle and font family became live once artist-level handlers existed. | Marked "Applies on the next run"; the panel raises a `rerun-needed` event. |

`apply_live` only touches artists that currently sit at the *current*
rcParam default (e.g. a line whose linewidth equals `rcParams["lines.linewidth"]`).
A line the user drew with `lw=3` is left alone, which mirrors what a re-run
would do. The same comparison drives `introspect_figure`'s
`overridden` list ("set in your code"). It is a heuristic — a user who
explicitly passes the default value is indistinguishable from one who
didn't — and the README says so.

`set_style()` resets and moves `mpl.rcParams` between runs, but the
retained figure's artists do not move with it — so right after a style
change, `mpl.rcParams[key]` no longer describes the value the figure was
actually drawn against, and comparing an artist to it makes every artist
look user-set (live preview then silently stops applying). `apply_live`
takes an optional `previous` dict of rc keys to the JSON values the panel
believes the figure currently sits at — recorded from the last
`introspect_figure()['rc']` plus the panel's own successful applies — and
uses it in place of `mpl.rcParams[key]` for the `only_defaults` comparison
whenever a key is present in it, falling back to `mpl.rcParams` otherwise.

## Python helper transport

Hosts already run "a small Python helper in a throwaway namespace, hand
JSON back to JS". The helper module is a **single file** (`core.py`) so it
can be inlined verbatim. Each call from JS is one snippet:

```python
<contents of core.py>
import json as __json
__plotpolish_result__ = __json.dumps(introspect_figure(**__json.loads('{"keys": [...]}')))
__plotpolish_result__
```

`FigureBackend.runPython` must resolve with the value of the **last
expression** as a string. A host that captures stdout instead appends
`print(__plotpolish_result__)`. Re-executing ~400 lines of Python per call
costs about a millisecond; if that ever matters, the snippet builder is the
one place to add caching.

Vite's `?raw` import is the "build step that inlines the Python": the
bundle literally contains `core.py`, so the JS and Python halves cannot
drift.

## Adapters

* `MemorySink` — tests and the demo's textarea editor.
* `ClipboardSink` — write-only (`getSource()` returns `null`). Tries
  `navigator.clipboard.writeText` and always also renders the block in a
  selectable `<textarea>`, because the clipboard API needs a user gesture
  and, in cross-origin iframes, a permissions-policy allow.
* `PyodideBackend` — reference `FigureBackend` over a `pyodide` instance
  the host has already loaded. Trinket's adapter will be copied from this.
* `MockBackend` — scripted responses for Vitest.

## Deliberately out of scope for 0.1

Per-artist editing (labels, limits, per-series color), any persistence
other than the fenced block, telemetry, remote asset loading, `figure.dpi`.

## Package name

`plotpolish`, chosen 2026-09-05; free on npm, PyPI and as a GitHub repo name
at that date. It describes the outcome rather than the mechanism, so it
survives the per-artist phase, and "polish" frames the tool as a finishing
step on code the user already wrote, which is design rule 1 in a word.
Also considered: `stylefence` and `plotfence` (name the fence), `figstyle`
and `styleblock` (plain), `rcknobs` (accurate for 0.1 only), `plotdials`
(over-promises live dials). The name appears in `src/constants.ts`,
`python/plotpolish/core.py` (fence text), `package.json`,
`python/pyproject.toml`, and the docs.
